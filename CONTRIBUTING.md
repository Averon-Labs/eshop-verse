# Contributing to EShop Verse

Thank you for contributing to EShop Verse. This document outlines the conventions and workflows for contributing to this project.

---

## Branch Naming

Use the following branch naming conventions:

```
feature/<short-description>   # New features
fix/<short-description>        # Bug fixes
refactor/<short-description>   # Code restructuring
chore/<short-description>      # Tooling, config, maintenance
docs/<short-description>       # Documentation updates
```

Examples:
- `feature/user-authentication`
- `fix/cart-total-calculation`
- `refactor/product-repository`
- `chore/update-dependencies`
- `docs/api-contract-pagination`

---

## Commit Conventions

Use [Conventional Commits](https://www.conventionalcommits.org/):

```
feat: add user registration endpoint
fix: correct cart item quantity validation
refactor: extract product mapper to separate class
test: add unit tests for order service
docs: document pagination conventions
chore: update Gradle wrapper to 8.x
build: configure ProGuard rules
ci: add Android lint check to workflow
```

**Rules:**
- One logical change per commit.
- Write clear, descriptive messages.
- Reference GitHub Issues: `feat: add login endpoint (#12)`.
- Keep commits focused and logically reversible.

---

## Issue Workflow

1. **Check existing issues** before creating a new one.
2. **Use issue templates** — Feature, Bug, or Task.
3. **Assign yourself** before starting work.
4. **Reference the issue** in your branch name and commits.
5. **Close the issue** via PR: `Closes #12`.

---

## Pull Requests

1. Create a PR from your feature branch to `main`.
2. Fill out the PR template completely.
3. Ensure all CI checks pass.
4. Request review from at least one team member.
5. Address review feedback.
6. Squash or keep commits clean before merge.

### PR Checklist

- [ ] Code follows project conventions.
- [ ] Tests are included and passing.
- [ ] Documentation is updated.
- [ ] No secrets or credentials committed.
- [ ] Commit messages follow conventions.
- [ ] PR description explains what and why.

---

## Code Review

### Reviewers Should Check

- Correctness and completeness.
- Adherence to architecture and conventions.
- Test coverage and quality.
- Security considerations.
- Performance implications.
- Documentation updates.

### Authors Should

- Self-review before requesting review.
- Keep PRs focused and reasonably sized.
- Respond to feedback constructively.
- Explain non-obvious decisions in PR comments.

---

## Testing

- All new code must include tests.
- Existing tests must continue to pass.
- Do not disable tests to bypass failures.
- See [docs/TESTING.md](docs/TESTING.md) for the testing strategy.

---

## Documentation

- Update relevant documentation when behavior changes.
- Update the API contract when endpoints change.
- Add ADRs for significant architectural decisions.
- Keep README and docs consistent with implementation.

---

## AI-Generated Code

Code generated by AI agents follows the same review process as human-written code:

- Must pass all CI checks.
- Must be reviewed by a human for non-trivial changes.
- Must follow all project conventions.
- Must include tests.
- AI-generated code is not exempt from any project rules.

Reviewers should pay particular attention to:

- Correctness of AI-generated logic.
- Proper error handling.
- Security implications.
- Unnecessary complexity or over-engineering.
- Consistency with existing codebase patterns.
